# Rubric: is this PR ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diff matches the plan, no silent drift | The branch's diff (`git diff main...HEAD`), compared against `plan.md`'s scope, files-to-touch, and approach sections, including anything recorded under `## Deviations` | Every change in the diff is named in the plan's scope or approach, or is explicitly documented under `## Deviations` with a stated reason. The diff makes no change the plan (plus its Deviations) does not account for. An undocumented change outside the plan's stated scope -- even a small one, even one that looks harmless -- fails this check. | required |
| Fix targets the cause, not the symptom | The diff's actual code change, compared against `plan.md`'s diagnosis | The diff's change acts at the point the diagnosis names as the root cause, not merely at the point the symptom was visible. An approach that only masks or works around the symptom fails, even if it makes the visible symptom disappear. A fix that deliberately narrows where a known-broken path can be reached, when the plan explicitly scoped it that way (stating what remains out of scope), is acting on the cause within the plan's own stated boundary and passes -- it is not symptom-masking merely because the broken path still exists elsewhere, unaddressed, when the plan said so. | required |
| Diff is clean and reviewable | The full diff, read as something a reviewer must read line by line | The diff contains no debug statements, no commented-out code, no unrelated formatting-only changes, and no edits outside what the plan's scope names. A diff a reviewer could not cleanly read top to bottom because of unrelated debris fails this check, even if the core fix inside it is correct. | required |
| Change is actually tested | The test evidence, compared against `plan.md`'s test plan | The test evidence shows actual before-and-after output from re-running the plan's PRIMARY stated repro steps (not a sentence merely claiming it passed), plus the result of running whatever automated test suite or checks the package's own repo actually uses, with that result shown, including an honestly reported failure. A secondary control case the plan's test plan also names (e.g. confirming an unrelated code path is unchanged) satisfies this check when reported as unchanged/passing, even without a full repeated transcript, PROVIDED the primary repro's before/after is fully shown -- do not fail this check merely because a control's identical-to-before result wasn't separately re-pasted. When the diff's change calls an existing function not itself shown in the diff (a shared formatter, logger, or error reporter), judge the test evidence's shown output for behavioral consistency with what that change does (the right error surfaced, the right exit code, the right data present), not for literal character-by-character derivability from the diff's visible lines. A missing before/after for the primary repro, a claimed-but-unpasted primary result, or output describing a clearly different behavior than the diff would produce still fails this check. | required |
| Description matches the diff | The draft PR description (`pr_draft.md`'s Summary and Changes sections), compared against the diff | Every behavior change in the diff is described, and the description claims no change that is not actually present in the diff. A description that is broader, narrower, or different from what the diff actually does fails this check, regardless of how well-written it is. | required |
| Standards and disclosure are met | The draft PR description, compared against the repo's own PR template and its own stated contribution/AI-use policy, plus the issue reference | Every section the repo's own stated PR template asks for is filled in with real content, and the issue is correctly referenced. AI-assistance disclosure is required by this check only when the package's own repo-facts or stated policy asks for or references AI-use disclosure; when a repo states no AI policy, the absence of a disclosure statement does not by itself fail this check. A policy that does ask for disclosure and receives none fails this check, as does a missing or placeholder template section. When precheck-grading your own draft PR before it has been opened (live mode), an unchecked "all CI jobs green" checkbox in the template does NOT fail this check on its own: CI cannot have run yet at this stage, this is the expected and correct state per the course's own stated instruction, and this check should judge only whether that box is left honestly unticked (not falsely checked) rather than penalizing its absence. This carve-out applies only to the CI-green item specifically, never to any other required template section. | required |

## Verdict rule

Accept only when every `required` check passes. Any `fail` or `unclear` on a required check means reject. `?` is treated as `unclear`, and `unclear` is treated as `fail` unless a specific check is explicitly marked not-yet-applicable for the mode being graded (for example, a check that needs the diff when only a draft description exists yet) -- in that case, exclude it from the verdict rather than counting it as a fail.
