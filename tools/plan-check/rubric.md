# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diagnosis matches the evidence | The plan's diagnosis section, read against the quoted repro evidence (actual output, error, or behavior observed) | The stated root cause is directly supported by the quoted evidence, not merely plausible or assumed. If the diagnosis goes beyond what the evidence shows, it is explicitly flagged as a hypothesis rather than stated as fact. A diagnosis that ignores or contradicts what the repro evidence actually showed fails. A diagnosis corroborated by multiple independent repro controls (e.g., the behavior present under one condition and absent under another, matching the hypothesis) counts as strongly evidenced and passes regardless of how confidently it is worded. A hedge elsewhere in the plan about a separate open question (which exact files, an untestable platform) does not itself weaken this check. | required |
| Scope is bounded | The plan's scope statement (what will and won't change) and its files-to-touch list | The plan names specific files or functions it will change, and states what it will deliberately leave untouched. A scope with no stated boundary, or one that extends further than the diagnosis requires without justification, fails. | required |
| Fix targets the cause, not the symptom | The plan's approach section, read against the diagnosis | The described approach addresses the root cause identified in the diagnosis. An approach that would only mask or work around the symptom (e.g. catching/suppressing an error without addressing why it occurs) fails, even if it would make the visible symptom go away. | required |
| A stranger could start executing it | The plan's approach and files-to-touch list, read as a set of instructions | Someone unfamiliar with this specific investigation could identify where to start and what the first concrete step is, without needing to infer missing context. Vague direction ("look into the parser") without a concrete starting point fails. When the exact file or function is not yet pinned down, a concrete, already-partially-executed investigative method (e.g., "traced with the tool's own debug flag, which already shows the origin") is a valid starting point and passes — vague intent to "look into it" with no method named does not. | required |
| Test plan is observable and reuses the repro | The plan's test plan section, read against the repro comment's steps | The test plan re-runs the actual repro steps already posted (not a new, different check invented for the plan) and states a concrete, observable expected result after the fix (specific output, specific behavior) — not just "should work" or "issue resolved." | required |
| Unknowns are stated as unknowns | The plan's risks/unknowns section, read against the rest of the plan's claims | Genuine uncertainty — an assumption not yet verified by the repro evidence or thread resolution, an untested edge case, or a part of the codebase not yet examined — is named as uncertain rather than presented as settled fact. A claim directly supported by the quoted repro evidence, by multiple corroborating control observations, or by a conclusion the issue thread already settled is NOT an unknown and needs no hedging, however confidently it is stated — confidence earned from cited evidence is not overconfidence. An explicit statement that no further risk was identified, with a stated reason, satisfies this check rather than failing it. Fail only when the plan treats something genuinely untested, unverified, or beyond what the cited evidence actually shows as if it were already confirmed. | required |
| Comment respects the thread and repo conventions | The draft plan comment, read against the issue thread's highlights and the repo-facts contribution-policy summary | The comment doesn't ignore relevant context already in the thread (a maintainer's steer, a note from another contributor) and follows any applicable repo convention, including required AI-use disclosure. Silence on a mandatory disclosure requirement fails this check. | required |

## Verdict rule

Accept only when every applicable `required` check passes; any `fail` or `unclear` on an applicable required check means reject. Preferred checks, if added later, never change the verdict. `?` is treated as `unclear`, and `unclear` is treated as `fail` unless a check is marked not-yet-applicable in plan-only mode (before the comment draft exists) — in that case, exclude it from the verdict the way your Unit 2 rubric did for report-dependent checks on a claim-only draft.
